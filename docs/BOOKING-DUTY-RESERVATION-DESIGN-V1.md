# Booking duty reservation V1: implementation contract

Status: draft implementation based on the existing buyer → manager → proposal → deal → terms → payment → secured booking → show advance flow. Depends on the confirmed performance window in PR #67. The manager duty window, private proposal snapshot, immutable feasibility review, atomic non-overlapping hold, first-payment cutoff, late-transfer reconciliation, auditable manual PO/credit, atomic booking creation with terms/milestones/hold, and atomic reservation-backed secured transition are implemented in this draft; **the migrations have not been applied and no runtime reservation or payment gate is installed.**

## Implementation checkpoint — 28 September 2026

- `ns_create_booking_with_hold_v1` now creates the pending booking, database-derived buyer terms, both milestone schedules, evidenced feasibility review and exact hold in one transaction. A failure rolls everything back. Retries with identical review/cutoff return the original booking/reservation; different evidence or a stale hold requires explicit recovery.
- The admin form shows the frozen duty block/location and requires a human travel/nearby-obligations review plus an explicit hold cutoff in the event zone. The RPC rechecks locked deal, selection, manager offer and proposal. Buyer pricing retains detailed proposal components when they match the locked deal, otherwise the existing aggregate format.
- Creation and milestone inserts require a private transaction authorization. Issued terms and milestone snapshots cannot be silently replaced/deleted. Buyer terms links expire by the hold cutoff; the database rejects acceptance without the exact live hold. App paths fail closed until the creation RPC is installed.
- Automated PostgreSQL tests use a schema-only fixture (no user rows) and PGlite 0.5.8 / PostgreSQL 18.3. They exercise actual PL/pgSQL, constraints, role permissions and rollback. Production is PostgreSQL 17; multi-session race/deadlock and full migration compatibility tests remain cutover gates. Unrelated table FKs/recovery triggers are outside this fixture.

### Cancellation/recovery checkpoint — 29 September 2026

In one transaction it cancels still-pending buyer requests and milestones, releases the exact secured duty reservation, cancels booking/brief, and settles the cancellation case.
2. An evidenced late transfer with pending reconciliation blocks finalization and slot release. A rejected late-transfer decision may then have its payment request cancelled; an accepted late transfer remains paid and immutable. Paid/refunded evidence is retained as ledger history.
3. Direct SQL transitions to cancelled booking/brief, released reservation, cancelled buyer request or settled cancellation case require private same-transaction authorization. Existing buyer terms and payment URLs stop resolving after the booking/request is cancelled.
4. `ns_guard_recovery_booking_sequence_v1` continues to block final cancellation while recovery is active; the finalizer also locks and rechecks the recovery row before releasing the original slot. Replacement security still requires reconciliation readiness.
5. `ns_abandon_pending_booking_v1` now handles an explicit zero-money withdrawal before security in one transaction: it freezes actor/reason and whether terms were accepted, revokes pending buyer payment requests, cancels pending milestones, releases the exact held reservation and cancels booking/brief. ## Verified current behavior

- `ns_record_availability_response_v2` records manager-confirmed **performance** hours; the date-wide `talent_availability` row is a search signal. Neither records arrival, setup, travel, nor the whole period for which a talent must be unavailable.
- A proposal freezes performance hours in `proposal_items`. Booking creation verifies them against the offer and places them in the immutable buyer terms snapshot. Buyer terms acceptance precedes payment request issuance.
- `ns_create_buyer_payment_request_v1` checks accepted terms and offer validity before the first request. `ns_record_buyer_payment_v1` records actual paid evidence. `ns_secure_booking_v1` checks offer validity again. Direct database writes can also reach `payments` or `bookings`, subject to existing triggers. The current payment request has a due **date**, not an expiration **instant**.
- `ns_finalize_cancellation_v1` sets the booking status to `cancelled` only after financial reconciliation. Recovery may start while the original booking has not yet been finalized as cancelled. The original must keep its reservation until a documented release decision.
- The production database had no `bookings` rows when checked on 28 September 2026, 01:xx WIB. This is a cutover observation, not a permanent assumption or evidence that test briefs are real work.

## Required data and invariants

| Record | Minimum fields | Rule |
| --- | --- | --- |
| Manager duty confirmation | `talent_offer_id`, local duty start/end with IANA event zone, event place, manager confirmation time | Duty interval covers arrival, preparation, performance and release. Convert to UTC instants once, using the named event zone. Enclose the confirmed performance interval, including a next-day end. A material change requires a new proposal and buyer terms. |
| Proposal snapshot | Confirmed duty start/end instants and place, linked offer and performance window | Freeze the exact commitment. Keep private duty details away from public search; show the agreed performance hours to the buyer. |
| Admin feasibility review | Booking/selected offer, nearby commitments, travel/turnaround evidence, reviewer and timestamp | Required before a hold, even where another engagement is only tentative or from an external calendar. No computed distance alone can approve an impossible transfer. Same-day non-overlapping shows can proceed with an evidenced review. |
| Reservation | Booking, talent, UTC `[start,end)` interval, state, expiry, release reason, revision/audit | Only one active reservation per booking. Reject overlapping **active** intervals for one talent with a database exclusion constraint, including crossing midnight or time zones. Preserve locked secured intervals; no unique talent/date index. |
| Payment request | Existing immutable payment snapshot plus an explicit expiry **instant** | A request expires no later than its live hold and valid offer. The buyer link must show the cutoff. Due date remains a contractual date and cannot substitute for the expiry instant. |

## State transitions

1. Admin reviews other obligations and verifies manager duty hours. **Before exposing the buyer terms link**, a single database transaction rechecks selected proposal, locked deal and valid offer, creates the pending-security booking, freezes buyer terms and payment milestones, and obtains an active `held` reservation. A failure leaves neither a promise nor a booking that appears ready. Idempotent retries return the same booking and hold.
2. Signed buyer acceptance applies to the existing immutable terms. If the hold has expired, acceptance must fail; retry requires reconfirmation before presenting terms again. Never silently update a snapshot already accepted.
3. Issuing the first buyer payment request requires the same active hold and a payment expiry before both hold and offer expiry. Repeated requests for the same milestone return the same still-valid snapshot. If the request is expired, revoke it and its buyer link before releasing the hold; block a late `paid` update and handle any actual late transfer through a separate reconciliation/refund procedure.
4. The paid-evidence transaction and the `secured` transition each require that same booking's active, non-overlapping reservation. Manual PO/credit security uses the same requirement. On securing, atomically convert `held` → `secured` and retain the interval without expiry.
5. An unpaid, unissued hold may expire under a serialized cleanup operation. Never free a hold while a live payment request or recorded buyer payment remains. Explicit pre-security abandonment must revoke links, resolve money if any, record who/why, and release in one controlled transition.
6. Cancellation/recovery keeps the original reservation until financial and replacement sequencing requirements allow release. Rebooking, postponement, or changed duty hours creates a new agreed snapshot/review; it cannot mutate an accepted or secured reservation in place. Show Advance can refine logistics but cannot silently overwrite the already secured duty interval.

Enforce these transitions inside the database. A route-level availability query is advisory: two concurrent requests can both pass it. Serialize per talent and use an exclusion constraint or equivalent transactional protection against overlaps. Triggers must close direct-write paths for payment request creation, marking paid, manual security, and booked status changes; do not replace existing commercial/acceptance guards. Maintain consistent lock order to avoid deadlocks.

## Payment cutoff decision for V1

For the first payment request, resolve the contractual due date in the event time zone and use 23:59:59 on that day as the payment cutoff. Require the manager offer and hold to remain valid through that instant; if either expires sooner, reconfirm before issuing the request. Expired links reject a new payment confirmation. A verified late transfer enters admin reconciliation, with the slot held until its outcome is recorded; the system neither secures the booking automatically nor offers that slot elsewhere.
